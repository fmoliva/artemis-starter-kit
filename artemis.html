What is it

One agent.
End-to-end QA coverage.

Artemis combines automated test execution, exploratory testing, load testing, bug analysis, and continuous improvement into a single AI-powered workflow.

🧪

Scripted Test Execution

Runs existing test cases against any web app using Playwright MCP (Chromium). Reports pass/fail with screenshots, console errors, and network logs — not just "it failed."

🔍

Autonomous Exploration

Crawls the app breadth-first, harvests all interactions, probes forms for edge cases and security issues — finding bugs that no one thought to write tests for.

⚡

Real Load Testing

Identifies critical API endpoints, generates actual k6 scripts for baseline, stress, spike, and endurance scenarios. Real numbers: P95 latency, error rate, throughput.

🛠

Self-Healing Selectors

8-level selector hierarchy with 3-retry self-healing. Tests don't break on minor UI changes — they adapt, annotate confidence, and flag fragile selectors for improvement.

🗄️

SQLite Persistence

All test cases, results, and bugs live in artemis.db. No folder confusion, no lost history — query TCs in milliseconds instead of reading 500-line files.

⚡

15× Faster TC Loading

DB queries replace file reads. A Quick Action that previously consumed ~1,200 tokens reading a markdown file now uses ~80 tokens from a single SQL query.

App-Agnostic

Works on any web app.
Not just the one it was built on.

Artemis has no hardcoded assumptions about the app it's testing. Give it a URL and it figures out the rest — whether you're testing a hospital system, a clinic portal, an e-commerce site, or an internal admin dashboard.

🌐

Any Browser-Accessible Web App

Playwright MCP drives a real browser. If a human can open it in Chrome, Artemis can test it — regardless of stack, framework, or domain.

📋

Bring Your Own Test Cases

Upload existing test scripts from a .doc / .docx file and Artemis parses them into its structured format automatically via /parse. Numbered lists, prose, tables — any format works.

🔍

Start With Zero Test Cases

No existing tests? Run /explore first. It crawls every page, probes every form, and generates a complete test suite from scratch — then you execute it.

Commands

12 Ways to Use Artemis

Each command activates a specific agent path. Start with /artemis for the full pipeline.

/artemis [url] [scope?]

Full Pipeline — Main Entry Point

Runs the complete 7-agent pipeline. Parses test cases, executes them in Playwright, runs exploratory QA, generates k6 load tests, analyzes all bugs found, reviews the test suite, and produces a combined QA + Performance Report.

part-1-orchestrator part-3-playwright-runner part-4-exploratory-qa part-5-load-test-agent
/run [scope] [url]

Playwright Runner

Execute a specific scope of test cases against a URL. Generates `.spec.ts` files and inline pass/fail results with screenshots on failure.

part-3-playwright-runner part-8-browser-tools
/explore [url] [area?]

Exploratory QA

Autonomous browser crawl. Maps all pages, probes every form and table, generates new test cases from what it discovers, identifies coverage gaps vs. existing test suite.

part-4-exploratory-qa part-10-ai-test-generation
/load [url] [scenario?]

Load Testing

Scores API endpoints by business criticality, proposes 4 load scenarios (baseline/stress/spike/endurance), and generates production-ready k6 scripts after approval. Baseline is always safe — Stress, Spike, and Endurance require a staging environment confirmation before running.

part-5-load-test-agent ⚠ staging only for stress+
/bug [jam-url]

Bug Analyzer

Deep-dives a specific failure. Pulls console logs, network failures, and user event timeline from Jam.dev recordings. Produces a full bug report with root cause hypothesis and a regression TC.

part-6-bug-analyzer
/improve [test-file]

Test Improvement

5-axis review of the test suite: redundancy, coverage gaps, assertion strength, selector fragility, test independence. Presents findings before applying any changes.

part-7-test-improvement part-9-selector-strategy
/parse [file-or-text]

Test Case Parser

Converts any input into structured test cases saved to the living test library. Accepts .doc / .docx files, Markdown, numbered lists, or plain prose. Flags vague or ambiguous items for review before saving.

part-2-test-case-parser .docx supported
/dashboard

Live Dashboard + TC Checklist

Two tools in one command. Starts the Artemis Live server for real-time automated run monitoring — and rebuilds artemis-tc-list.html, a self-contained manual QA checklist organized by module → submodule. The checklist auto-rebuilds whenever new TCs are added via /parse, /explore, or /improve.

artemis-live.html artemis-tc-list.html server.js
/port [source] [app-name] [url?]

TC Portability

Copies applicable test cases from an existing project to a new app. Presents a module mapping table for approval, scores each TC for portability, wraps app-specific text in [REVIEW:] tags, reassigns IDs using the target prefix scheme, and rebuilds the dashboard.

part-12-tc-portability module mapping [REVIEW:] tags
/matrix [module?]

Coverage Matrix

Reads your test library and generates a Feature × Test-Type grid — Happy Path, Edge Case, Error Handling, Security, Performance. Instantly see which modules are missing security probes or error handling TCs before something slips through.

reads test-cases/ no browser needed coverage-matrix.md
/diff [source] [target] [module?]

TC Library Diff

Compares two projects' test case libraries. Shows TCs unique to each, diverged steps, and unresolved [REVIEW:] tags left over from a /port. Useful for tracking how a new app's suite grows over time.

reads test-cases/ no browser needed tc-diff.md
/scope [url] "feature-description"

Regression Scope

Tell Artemis what changed in plain English. It scores every TC for relevance — by module match, action verbs, and field names — then picks the top 20 most likely to catch a regression and hands you a pre-filled /run command.

part-13-regression-scope relevance scoring pre-filled /run

Cognitive Modes

One Claude.
Seven Mindsets.

Artemis doesn't spawn separate processes. Claude shifts its cognitive mode to embody each specialist agent — the way a senior QA engineer thinks differently when writing tests vs. debugging vs. reviewing.

Coordinate

QA Orchestrator

Routes the pipeline, tracks parallel threads, merges results from all three execution paths. Decides what to skip, what to prioritize, what to surface in the executive summary.

Parse

Test Case Parser

Extracts structure from chaos. Converts any format into standardized TCs. Infers intent, flags ambiguity, never silently discards a test case. Maintains TC numbering continuity.

Execute

Playwright Runner

Trust nothing. Assert only what is observed. Screenshot on every failure. Every result is evidence-based — PASS means it was seen, FAIL has a screenshot and URL to prove it.

Explore

Exploratory QA + UI Discovery

Curious and adversarial. Maps every page, tries every form field, looks for what testers forget to test. Finds security probes, empty states, edge cases, and unexpected flows.

Perform

Load Test Planner + Generator

Identifies choke points, thinks in concurrent users. Generates real, runnable k6 scripts — not simulated traffic, not estimates. P95, error rate, throughput against real thresholds.

Analyze

Bug Analyzer

Root cause over symptoms. Reproduces minimally. Classifies by layer (UI/API/Data/State/Timing). Enriches every bug with Jam.dev console logs, network failures, and user event timeline.

Improve

Test Improvement Agent

Senior QA code reviewer. Every test must justify its existence. Scores on 5 axes, presents findings, gets approval, applies changes, appends improvement history. The test suite evolves.

Core Principles

What Artemis
always does.

1

Explore before asserting

UI reality overrides specs. Artemis navigates the live app before making any assertions — what's in the browser matters more than what's in the document.

2

Evidence-based results

Every PASS was observed. Every FAIL has a screenshot, URL, expected result, and actual result. No result is reported from memory or assumption.

3

Self-healing selectors

3-retry protocol with 8-level selector hierarchy before marking an element not found. Tests adapt to minor UI changes instead of failing on them.

4

Living test library

The test-cases/ directory is a versioned artifact. TC IDs are permanent. Tests are improved continuously — never silently deleted or overwritten.

5

Performance is a finding

/load generates real k6 scripts with measurable thresholds. Slow pages observed during functional testing are noted as observations — separate from test failures.

6

Security always in scope

Every form gets injection and boundary probes. XSS, SQL injection, path traversal, long strings, and unicode inputs are tested without being explicitly asked.

7

Never generate code without executing first

.spec.ts files are derived from observed browser behavior — not written speculatively. Selectors come from the actual DOM, not from reading the source code.

8

Results persist forever

Every test run, result, and bug is written to artemis.db — not just a markdown file. History survives server restarts. Bugs stay in the dashboard until marked resolved.

9

Always close Chromium after testing

Playwright MCP uses a dedicated Chromium instance — never the user's Chrome browser. After every test run, Chromium is closed immediately. The live dashboard runs independently and does not need the browser to stay open.

Human in the Loop

Artemis runs autonomously.
Until it needs you.

Artemis executes without interruption — no mid-run permission prompts, no approval requests for navigation, screenshots, or file writes. It pauses at exactly 5 defined gates where human judgment is required before continuing.

1

Pre-Run Confirmation

/artemis /run NEVER SKIPPED

Shows URL, scope, TC count, and which paths will run. Human confirms the target and scope before any browser opens or any test executes.

2

AI-Generated TC Approval

/explore /parse NEVER SKIPPED

AI-generated or converted test cases are shown with any inferred or ambiguous flags. Human reviews and approves before any TC is saved to the library.

3

Load Test Environment Check

/load BASELINE AUTO-RUNS

Before stress, spike, or endurance scenarios, human confirms the URL is a staging environment. If production — Artemis refuses. Baseline scenario always runs without asking.

4

Module Mapping Approval

/port NEVER SKIPPED

Before porting test cases between projects, Artemis presents the source → target module mapping table. Human confirms, corrects, or rejects mappings. Wrong mappings silently mis-route all ported TCs.

5

Test Improvement Changes Approval

/improve NEVER SKIPPED

After 5-axis review, Artemis presents all proposed changes — redundant TC removal, selector fixes, new AI-generated TCs. Human approves all, selects specific items, or rejects. No change is applied automatically.

Outside these 5 gates, Artemis proceeds autonomously. Navigation, screenshots, DB writes, bug logging, observations, Chromium close, and dashboard updates all happen without asking. Once Gate 1 is approved, the run executes to completion without interruption.

TC Portability

Reuse test cases
across apps.

When you build a second app that shares structural patterns with a tested one, /port migrates the reusable test library in minutes — not days.

🗺

Module Mapping Table

Compares source modules to target structure using exact, fuzzy, and semantic matching. EXACT and STRONG matches are auto-suggested. PARTIAL matches require your confirmation. Nothing is written until you approve.

🔍

Portability Scoring

Each TC is scored for app-specificity. Generic CRUD, validation, pagination, and empty state flows carry over untouched. Hardcoded URLs, product names, and org-specific terms get flagged with inline [REVIEW:] tags.

🔁

ID Reassignment + Traceability

New TC IDs are assigned using the target app's prefix scheme starting from 001 (or the next available ID). A Ported from: metadata line links each TC back to its source for full traceability.

Installation

Share Artemis with your team

Artemis lives inside Claude Code as a skill — a folder in ~/.claude/skills/. Share only the skill folder, not project data.

Easiest

Zip & Share

Zip the skill folder and send it. Your colleague unzips it in the right place and they're ready to go.

  • 1
    Zip the Artemis skill folder
    cd ~/.claude/skills zip -r artemis.zip artemis/
  • 2
    Share artemis.zip via Slack, email, or drive
  • 3
    Colleague unzips into their skills folder
    cd ~/.claude/skills unzip artemis.zip
  • 4
    Restart Claude Code — Artemis appears automatically
Best for Teams

GitHub Clone

Host Artemis in a private repo. Team members clone it directly. Push updates once — everyone stays current.

  • 1
    Push ~/.claude/skills/artemis/ to a private GitHub repo
  • 2
    Colleague clones directly into their skills folder
    cd ~/.claude/skills git clone git@github.com:yourorg/artemis.git
  • 3
    Restart Claude Code — Artemis is ready
  • 4
    To update later
    cd ~/.claude/skills/artemis git pull

What to share vs. what to keep private

Path Share? Why
~/.claude/skills/artemis/ ✓ Yes This is Artemis itself — SKILL.md, all reference docs, all templates
[app-name]/.env ✗ No Contains credentials — each person creates their own
[app-name]/test-cases/ ✓ Yes (optional) Living test library — share if you want the team to use the same TCs
[app-name]/results/ ✓ Yes (optional) QA reports — share for visibility, keep private if sensitive
[app-name]/app-guide.md ✓ Yes App-specific guidelines — safe to share, no credentials inside
